# 專案背景

## 專案名稱

TripFlow

## 專案摘要

TripFlow 是一個多日旅程規劃工具，建立在既有的單頁前端專案之上。
它的目標是把旅程、每日行程、候選地點與地點補充資訊集中管理，而不是只做一張靜態行程表。

這是一個 brownfield 專案。
目前系統其實已經支援實際可用的旅遊規劃流程，但在程式結構與資訊層級上，還需要整理後才能更好地成品化。

## 產品目標

這個產品不是旅遊內容網站。
它是一個旅行規劃工作台，重點在於：

- 管理多趟旅程
- 安排每日正式行程
- 區分正式行程與候選地點
- 透過 Google Places 補齊地點資訊
- 降低調整順序與改行程的成本

## 使用者

主要使用者：

- 規劃 3 到 7 天以上自由行的人
- 同時整理很多餐廳、景點、住宿與交通選項的人
- 想把正式安排與備案放在同一個地方管理的人

次要使用情境：

- 幫家人或朋友規劃旅程的人
- 在熟人小範圍內共用旅遊規劃工具的人

## 目前技術棧

- 前端：Vue 3（CDN）
- UI：Tailwind CSS（CDN）、Element Plus、Font Awesome
- 拖曳排序：SortableJS
- 開發 / build：Vite
- 資料：Firebase Authentication（匿名登入）、Firestore、Firebase Hosting
- 外部整合：Google Maps Places API

## 目前架構

- `public/index.html` 放主要模板與大量畫面結構
- `public/js/app.js` 放大部分應用邏輯
- `public/css/styles.css` 放共用樣式與補充樣式
- `public/config.js` 放 Firebase 與 Google Maps 設定

目前的架構優先考慮的是快速迭代，而不是可維護性。

## 重要限制

- 專案主要給自己或熟人小範圍使用，不是公開 SaaS
- 目前沒有要導入完整登入權限與多人協作系統
- 重構時要優先保留現有可用行為
- 專案之後要能更適合作為面試 demo，但不能失去原本的實用性

## 目前已有功能範圍

- 旅程管理
- 每日正式行程管理
- 候選地點池
- 全部地點檢視
- Google Places 地點資訊補齊
- 拖曳排序
- Firestore 即時同步

## 目前痛點

- `public/js/app.js` 太大，責任混在一起
- `public/index.html` 承擔太多不同頁面與視圖責任
- 首頁比較像列表，不像產品化 dashboard
- 正式行程與候選地點在產品層級上還不夠清楚
- 部署路線與 build 路線還沒有完全對齊

## 產品方向

接下來希望往這個方向調整：

- 把產品定位成旅程規劃 dashboard，而不是一般旅遊頁面
- 把首頁提升成旅程總覽
- 更清楚區分正式行程與候選池
- 降低後續修改成本，讓程式更容易擴充
- 強化面試 demo 時的產品敘事

## 開發慣例

- 優先做漸進式重構，不做一次性大翻修
- 視覺大改之前，先保留原本可用行為
- 將畫面 helper、資料模組與外部整合拆開
- 先把目前真實存在的行為寫成 spec，再處理後續變更
